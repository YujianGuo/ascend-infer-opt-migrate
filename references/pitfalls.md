# 迁移踩坑与排查清单

来自一次真实迁移：把 vllm-ascend PR #12647 的 GDN prefill 融合算子接到 A2 容器
（8×910B3、Qwen3.8-Flash-Next w8a8、TP8 + MTP）。每条给出症状、根因、判定方法和处置，
在其他工程上按同类信号复用，不照搬路径与命令。

## A. 代码路径归属：改了文件不等于生效

| 症状 | 根因 | 判定 | 处置 |
|---|---|---|---|
| 目标文件已改，行为/日志毫无变化 | 运行时加载的是另一份代码（安装副本、另一工作区、editable 映射指向别处） | 在目标进程内打印 `module.__file__`，与编辑路径比对 | 锁定真实加载路径后再改 |
| 文件确实是运行中的那份，改动仍不生效 | monkeypatch / 注册目标类与实际实例化的类不是同一个 | 从模型入口逐跳追：config → ModelRegistry → model 文件 → `self.xxx = SomeAttention(...)` → patch 目标 | 改真正被实例化的类或共享 patch 点 |
| 仓库同时存在 `amd/`、`nvidia/` 等多套 vendored 实现 | 运行时只加载其中一套（注册声明或 `sys.modules` 别名） | 查 ModelRegistry 注册项与实际 import 链 | 只改被加载的那套，或改两者共用的 patch 入口 |
| 平台分支（如 `is_310p()`）把调用导到另一套方法 | 分支判断与真实 SoC 不一致 | 目标进程内直接求值该判断 | 按真实分支验证，不按标签假设 |
| 模型执行期 INFO 日志不落盘，"代码好像没跑" | 镜像/框架日志配置在推理阶段过滤了 INFO | 用一次 WARNING 级日志做可见性预检（见 G 节） | 不要用日志缺失推断未执行 |

规则：

1. 动手做归因前，先花 1 次极小实验确认"日志能出来、代码确实进到该函数"，再判断逻辑分支。
2. 归因结论只认运行时证据（日志 / 计数 / dispatch 记录 / profiler），不认"文件里写了"。
3. 大框架里一次完整的"入口→实例→patch 目标→算子分发"链式确认，通常比反复重启省时得多。

## B. 算子契约：文档不够时用退化输入探针

文档常有歧义（尤其 state 的 `[..., Dv, Dk]` 与 `[..., Dk, Dv]`、head 映射、scale 作用位置、
是否内含 cumsum/L2 norm）。用退化输入直接把语义读出来，比反复调参快：

| 探针 | 构造 | 读出什么 |
|---|---|---|
| 布局探针 | `T=1`、`beta=0`、`g=0`、给非对称 `initial_state=S` | `out = f(S,q,scale)`：把候选布局（S 与 S.T）分别送入并与参考比对，`max_abs` 小者即真实布局 |
| 头映射探针 | `T=1`、`S` 只在对角元素非零、`q` 各 head 取不同常数 | 每个 value head 取到哪个 query head（repeat_interleave vs tile） |
| 状态更新探针 | `S=0`、`beta=1`、`v=e0`、`g=0` | `final_state = k_head ⊗ v`，同时确认 key head 映射与返回布局 |
| 归一化/衰减探针 | 输入已归一化 vs 未归一化；`g` 传原始 log 值 vs 已 cumsum | 判定算子是否内部做 L2 norm、chunk 内 cumsum |

要求：探针结论写成"实测确认"并落到迁移记录，不把文档表述当事实。
可直接改 [算子契约探针模板](../assets/operator-contract-probe.py)（layout / headmap / norm 三种模式）。

## C. 补丁落地：目标文件可能早已偏离源基线

| 症状 | 根因 | 处置 |
|---|---|---|
| 源 PR 补丁 `git apply` 上下文冲突 | 目标工作区有他人/前序会话改动，或目标版本已重构 | 先 `git diff -- <file>` 看目标现状，按目标结构做等价改造，不机械 apply |
| 交付的补丁混入无关改动 | 工作区本身有未提交变更 | 重建 pre-image（反向移除本次新增块或从 HEAD + 既有改动还原），`diff -u` 生成只含本次增量的 focused patch |
| 回滚把别人的改动冲掉 | 用 `git checkout` / `git stash` 整体回退 | 只反向应用本次补丁；共享工作区禁止整体回退 |

补丁自检（缺一不可）：

1. `git apply --check <patch>` 在前像上通过；
2. 应用后与部署文件逐字节一致（`diff`/`md5sum`）；
3. 在已部署的工作区上 `git apply --check --reverse` 通过（证明工作区 == 补丁结果）。

## D. 共享容器与会话卫生

| 症状 | 根因 | 处置 |
|---|---|---|
| 新服务启动报 `Free memory on device (x/60.96 GiB) is less than desired GPU memory utilization` | 上一轮进程/HBM 未释放，不是启动参数错 | 清理旧进程后重启；不要急着调 `gpu-memory-utilization` |
| 清理命令执行后进程仍在 | `pkill -f "关键字"` 的模式匹配到了执行它的 shell（cmdline 含关键字），把自己杀了，后续命令未执行 | 用锚定模式（如 `pkill -9 -f "^VLLM::"`）或 `pgrep` 后排除自身 |
| 宿主机 `kill` 无效 | 容器内进程属 root，宿主机普通用户无权限 | 在容器内以对应用户执行清理 |
| `npu-smi` 里仍有 PID | 可能是僵尸进程（`Z` 状态），不占 HBM | 以 `npu-smi info` 的 “No running processes” 为释放判据 |

重启前置检查：旧 API server 与 worker 全部退出 → `npu-smi info` 全部空闲 → 再用同一份启动脚本重启，
并记录本次会话使用的开关值，避免 A/B 两臂脚本漂移。

## E. 测量设计：先让信号大于噪声

| 现象 | 结论 |
|---|---|
| 混合线上负载（8k/1k、并发 8）会话间漂移约 10%，优化效应约 4% | 该负载下吞吐类指标"噪声内、不成立"，只可辅证 TTFT 方向 |
| 换成隔离负载（8k in / 1 out / 并发 1，TTFT 由 prefill 主导）后重复内波动 < 0.3% | 同一次会话内 3 次重复即可分辨 3%~4% 的效应 |

实验设计最低要求：

1. 与优化目标匹配的隔离负载（Prefill 看 TTFT、Decode 看 TPOT/ITL），不要只用混合吞吐；
2. 每个配置至少 2 个独立服务会话，用会话间差异估计漂移；
3. 每个会话至少 3 次重复，用重复间差异估计测量噪声；
4. 效应量需大于会话漂移才可下结论，否则如实写"噪声内/证据不足"，不挑最快样本。

## F. 精度判定：先扣掉模型自身非确定性

MoE 路由、投机解码、bf16 原子累加等会让同一配置两次运行结果不同。判定流程：

1. 先在同一配置下重复采样，得到"噪声底"（本次案例：同配置首 token logprob 极差 0.02~0.11）；
2. 再比较跨配置差异（本次：0.012，均值），**小于噪声底即不可判为回归**；
3. 贪心文本在非确定模型上也会分叉，不能用单次 ON/OFF 文本不同判定精度问题；
4. 算子级精度用 fp32 参考实现比对（误差应落在目标 dtype 的舍入量级），作为模型级的支撑证据。

## G. 日志与 tracing 限制

| 现象 | 根因 | 处置 |
|---|---|---|
| 模型执行期 INFO 不出现，配置期 INFO 正常 | 推理阶段日志被过滤/未落盘 | 归因日志用 WARNING 级，并挂在显式 debug 开关下（如 `*_DEBUG=1`） |
| 加 `print()` 后编译或启动直接失败：`torch._dynamo.exc.Unsupported: Failed to trace builtin operator print` | `torch.compile` 会追踪该 forward | 不要把 `print` 放进被追踪的 forward；日志放在自定义 op 内部（不被追踪）或改用日志函数 |
| `*_once` 日志"没打印" | 该消息可能已在 profiling/dummy run 阶段被消费 | 归因日志的 key 要区分阶段，或改用计数器后统一输出 |

## H. 收益幅度不可移植

同一机制在源端（A5/A3、另一模型）记录 16%，在目标端（A2、跨模型）实测 3.7%：
只迁移**机制与触发条件**，收益幅度必须由目标端同环境配对实验得出，并在报告中区分
"机制已验证"与"收益达标"。

## I. 重启成本要提前计入计划

模型加载 + 编译 warmup 常见 10~15 分钟/会话。开始 A/B 前先规划最少会话数
（每臂 ≥2 会话），把待测项做成**一个**环境变量或配置项，避免为多个小改动反复重启；
同时准备一个与基线完全一致的启动脚本，只在被测开关上不同。

## J. 证据链最小集合（缺一条就不能下结论）

| # | 证据 | 采集方式 | 反例（不成立的替代） |
|---|---|---|---|
| 1 | 运行的是哪份代码 | 进程内 `module.__file__` / 包版本 | “我改了仓库里的文件” |
| 2 | 优化路径确实命中 | debug switch + WARNING 日志 / dispatch 计数 / trace | “分支写在代码里” |
| 3 | 算子级等价 | fp32 参考实现比对，误差落在 dtype 舍入量级 | “跑通了、输出看着正常” |
| 4 | 精度噪声底 | 同配置重复采样极差 vs 跨配置差异 | 单次 ON/OFF 文本差异 |
| 5 | 性能配对 | 隔离负载 + ≥2 会话 × ≥3 重复 | 单次混合负载吞吐 |
| 6 | 回退可用 | 开关置 0 的完整会话 + 能力不满足时的自动回退 | “有 fallback 代码” |
